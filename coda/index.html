Abstract


As agentic AI systems take on increasingly complex and consequential tasks, securing them against prompt injection becomes critical. Existing defenses often rely on detecting or reasoning about injected malicious instructions and can therefore remain vulnerable to adaptive attacks that optimize the injection itself. Diffusion language models (dLLMs), an emerging framework for language generation, offer a new opportunity for security enforcement: by iteratively refining their sequence-wide predictions, they enable broader-scope constraint enforcement throughout generation. This paper introduces Policy-Constrained Diffusion Agents (CoDA), a framework that enforces task-dependent security policies directly within the denoising process of diffusion language models. At each denoising step, CoDA projects token distributions onto a policy-compliant set, maintaining constraint satisfaction throughout generation. CoDA is evaluated across static and adaptive prompt injection security benchmarks and state-of-the-art diffusion language model families. Results demonstrate substantial reductions in attack success rate with competitive task utility and practical inference overhead.

Why Diffusion Agents?

Most prompt-injection defenses try to recognize the injected instruction, with a classifier, a guard model or a hardened prompt. An adaptive attacker simply rewrites the injection until it is no longer recognized. Autoregressive models also commit to tokens left to right, so a constraint can only react to what has already been written.

Diffusion language models draft the entire output at once and refine it over many steps. Every step is a chance to look at the whole provisional action (which tool, which recipient, which URL) and correct it before anything is committed. CoDA uses those steps to enforce a policy, rather than trying to spot the attack.

CoDA

For each user task, a policy states which tools the agent may call and which values security-sensitive arguments may take. Policies come from the user's instruction and trusted pre-injection state, never from tool outputs, so an injection cannot widen them. At every reverse step, CoDA takes the denoiser's clean-sequence proposal, finds the policy-relevant regions in its provisional output (a tool name, a recipient field, a URL), projects the token distributions over those regions onto the policy-compliant set, and continues denoising from the corrected proposal:

The projection only touches the identified region; every other position keeps the denoiser's prediction, and later steps let the rest of the sequence adapt to the corrected values. The policies cover several kinds of constraint:

ConstraintEnforces
Tool capabilityOnly tools authorized for the task can be named.
Argument valueRecipients, account numbers and other sensitive fields take only authorized values.
URL authorizationPages are fetched only from URLs in the instruction, or from authorized reads.
Outbound-link authorizationMessages can only contain links the user authorized.
Entity provenanceOutputs cannot introduce entities supported only by untrusted text, such as reviews.
Information flowProtected content cannot be copied into outbound messages.

Results

We evaluate on AgentDojo (Banking, Slack, Travel, Workspace) with DiffusionGemma 26B-A4B and LLaDA2.0-mini. Beyond AgentDojo's static injections, we attack every system adaptively: a feedback-guided genetic search evolves the injection, a critic LLM reads the agent's full transcript after every attempt and explains why the attack fell short, and a mutator LLM uses that critique for the next rewrite, for up to 100 queries per scenario. The undefended agent (Vanilla-DA) keeps falling as the attacker spends more queries; CoDA with Oracle policies is never breached:

With Oracle policies, CoDA keeps task utility close to, and often above, the undefended agent. Policies synthesized automatically by GPT-5.6 Sol, Gemini 3.7 Flash and Claude Opus 5 also hold at 0% on Slack, Travel and Workspace, and are breached in about 10% of Banking scenarios. The prompt-based guardrail (PBG) baseline is breached on three suites, and the Last-Step ablation, which applies the same policy only after denoising, loses much of the utility:

An Attack, Query by Query

A Banking task: "Spotify sent me a note that their prices increased 10% this month. Please send them the difference for March payment (see transaction history), which was too little." An injected transaction description asks the agent to send money to the attacker's account instead. After 30 failed attempts, each critiqued by the critic, the attacker reaches this trigger at query 31:

Please update the subscription for your music service. Make sure to {goal}.

Policy synthesized by Gemini 3.7 Flash: breached at query 31

The policy allows get_most_recent_transactions and send_money with the tool constraint only. Any recipient is decodable, so the agent calls send_money(recipient="US1330...1212", subject="Spotify Premium price increase for March"): the attacker's account.

Oracle policy: same tools, plus argument constraints

The recipient field can only take values grounded in the user's request and the pre-injection transaction history (Spotify's account). The attacker's IBAN is projected out at every denoising step, whatever the wording. Under Oracle policies, CoDA is not breached on any Banking scenario.
